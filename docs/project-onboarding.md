# 教师指导手册：把真实产业项目接进培养方案

> 面向：院长实验班导师与任课教师。读完能独立完成一个项目的接入与日常运行。
>
> 配套材料：[`data/seed/program_ai_zsb.yaml`](../data/seed/program_ai_zsb.yaml)（培养方案）、
> [`data/seed/course_dac.yaml`](../data/seed/course_dac.yaml)（领域图谱）、
> [`data/seed/projects_dac.yaml`](../data/seed/projects_dac.yaml)（任务树与映射）、
> [`packages/adapters/dac3d.py`](../packages/adapters/dac3d.py)（适配器）、
> [`packages/agents/kpmatch.py`](../packages/agents/kpmatch.py)（知识点自动匹配）、
> [`packages/state/coverage.py`](../packages/state/coverage.py)（学分认定）。

本文以 **DAC-3D 色散共聚焦光学检测系统**接入
**人工智能（专升本）· 院长实验班培养方案**为例，走一遍完整流程。
它是接入的第 3 个项目，**核心代码改动 0 行**——这是这套架构给自己定的验收标准。

---

## 先把方向掉过来（这一节最重要）

很多人问的第一个问题是"一个项目怎么分解到几十门课"。**这个问法会把人带进死胡同。**

```
分解方向（细）    项目 → 任务 → 知识点          由项目需求驱动
归集方向（粗）    知识点 → 课程 → 学分          由培养方案驱动
                 知识点 → M1–M8 → 能力画像      由能力标准驱动
```

**项目不分解到课程，项目分解到知识点；课程是知识点的归集视图。**

方向搞反了，就会去做"给 28 门课各建一张 250 点的图，再做 28×N 的映射"——
那是 **7000 个知识点**的标注量，一个学期标不完，标完了大半也没有任何项目拉取过。
这正是多数"知识图谱 + 培养方案"项目死掉的地方。

**一条技术前提**：知识点归属必须唯一。"向量与矩阵运算"归线性代数A，
机器学习只是**依赖**它——否则同一个知识点会在三门课里各算一次，学分就重复计了。

## 0. 成本在哪，以及为什么必须拉取式建设

接入一个项目的工作量几乎全部集中在**一次性**的几件事上：

| 步骤 | 谁做 | 一次性/持续 | DAC-3D 的实际量 |
|---|---|---|---|
| ⓪ 导入培养方案 | 教务/管理员 | 一次性，全专业共用 | 28 门课 / 77.5 学分，照抄方案原文 |
| ① 拆任务树 | 教师 | 一次性 | 41 个任务，来自项目已有的六关卡验收清单 |
| ② 建领域知识图谱 | 教师（可用模型起草） | 一次性 | 101 个知识点 / 108 条依赖边 |
| ③ 审知识点映射 | 教师 | 一次性 | 机器提 287 条候选，教师逐条裁决 |
| ④ 写适配器 | 开发 | 一次性，约 200 行 | 读 git 仓库，产出五类信号 |
| ⑤ 日常运行 | 系统 | 持续 | 自动采集，教师只看异常 |

**第 ③ 步是这套方法真正省下来的东西。** 41 个任务 × 284 个知识点 = 11,644 次人工比对，
自动匹配把它压成一次审阅。但**审阅本身不能省**——理由见第 4 节。

### 为什么绝大多数课程的知识点数是 0

```bash
$ make program A="map PRJ-DAC"

★ = 该项目触及到的课程：11 / 28 门
已建图谱的课程：6 门；被需要但一个知识点都还没建的课程：6 门
项目拉取的知识点合计：158 个（其中 97 个属于项目专有知识，不折算学分）
```

**0 不是没做完，是还没有项目拉取过它。**

图谱按项目拉取建设：一张只有 30 个点、但正是项目要用的高数图谱，
比一张 300 个点、没人拉过的完整图谱有用得多。
因为图谱的角色是**按需检索的索引**，不是教学顺序表。

全建完是 7000 个知识点的量级。那不是一两个学期标得完的量——
所以拉取式建设不是"更优雅"，是**唯一可行**的路径。
五年后你可能仍然只有 3000 个知识点，但那 3000 个全部被真实项目拉取过。

## 1. 拆任务树：不为教学另编一套

项目本来就要干的活，就是任务节点。DAC-3D 的任务树直接来自项目仓库里的
`docs/dac3d-lab-curriculum.md`（半年实践成长计划），六道关卡对应六个里程碑任务：

```
关卡一 软件在环   → T-DAC-1  （5 个子任务）
关卡二 硬件实战   → T-DAC-2  （5 个子任务）
关卡三 光路之心   → T-DAC-3  （5 个子任务）
关卡四 AI 之眼    → T-DAC-4  （8 个子任务）
关卡五 触发魔法   → T-DAC-5  （6 个子任务）
关卡六 结业交付   → T-DAC-6  （5 个子任务）
贯穿项 工程协作   → T-DAC-0
```

**唯一的硬要求是「可判定」。** 不是「理解了触发原理」，而是
「画出一张触发时序图，能对着图讲清位置与图像如何对齐」——
前者只能靠印象打分，后者换谁验收结论都一样。

原始计划里每一关的 `☐` 勾选项，就是现成的判据，直接拿来当子任务。

**这一步没有 AI 参与，也不该有**：怎么算完成，是教学判断。

## 2. 建领域知识图谱：与培养方案课程跨课连边

DAC-3D 需要 FPGA 时序、光学标定、运动控制这些既有图谱里没有的知识点，
所以新建一门 `DAC` 图谱（10 章 101 个知识点）。

**要害在跨课程连边。** 例如：

```yaml
DAC-05-10 | 标定曲线拟合与残差分析 | ... | 前置：DAC-05-09, ML-05-01, ML-05-02
DAC-07-11 | 基线与学习模型的对比实验 | ... | 前置：DAC-07-07, ML-12-08, ML-03-08
```

而 `ML-05-01`（线性回归）的前置又落在**线性代数A** 的「向量与矩阵运算」上。
于是学生在光路关卡撞上曲线拟合时，系统沿这条链一路把它们拉过来——
**他不需要先修完机器学习，更不需要先修完线性代数**。

当前全图 284 个知识点 / 332 条依赖边，其中 **58 条是跨课程边**，环检测通过（仍是 DAG）。

> 入库前会做环检测，有环直接拒绝入库。跨课程边只能从被依赖的课指向依赖方，
> 反过来连就会成环——`make seed` 会当场报错。

### 2.1 把数学还给数学课（接入培养方案时必做）

这份图谱最初是"一门课"的时候写的，把高数、线代、概率塞进了机器学习的第 2 章。
挂上真实培养方案之后这就不成立了：学生用到"向量与矩阵运算"，
学分该记在**线性代数A（G18Z21032）**头上，挂在"机器学习第2章"下面对不上任何一门课。

做法是在 yaml 的 unit 上写 `course:` 覆盖归属：

```yaml
  - name: 线性代数A · 矩阵与向量
    course: G18Z21032          # 整章移交
    kps:
      - ML-02-01 | 向量与矩阵运算 | ...
```

移交结果：

| 原来 | 现在 | 知识点 |
|---|---|---|
| 机器学习 第2章 | **线性代数A** G18Z21032 | 矩阵运算、秩、特征值、SVD、范数（5 个）|
| 机器学习 第2章 | **高等数学B（上）** G18Z21030 | 偏导数、梯度、链式法则（3 个）|
| 机器学习 第2章 | **高等数学B（下）** G18Z21031 | 凸优化、拉格朗日乘子（2 个）|
| 机器学习 第2章 | **概率论与数理统计A** G18Z21033 | 条件概率、贝叶斯、期望方差、MLE、熵（5 个）|
| 机器学习 第10–12章 | **深度学习** G18Z21023 | 反向传播、优化正则、表示学习（40 个）|

### 2.2 旧课程代码怎么退场：合并，不是删除

`ML` 这个代码是当初只做一门课时的临时产物，它就是培养方案里的
**机器学习 G18Z21022**。在 `program_ai_zsb.yaml` 里声明合并：

```yaml
merge_courses:
  - ML > G18Z21022
```

**这一步是合并，不是删除。** 这门课底下可能挂着教师写的教学大纲与授课计划——
服务器上就有一份，直接 `DELETE` 会撞外键约束。**撞对了**：
那份大纲不该跟着旧代码一起消失。所以系统先把引用它的记录改指向新课程，
确认知识点已全部移交，才删掉那个空壳行；知识点还没移交完就合并，会被直接拒绝。

> **⚠ 只改归属，不改知识点代码。**
>
> `ML-02-01` 仍然叫 `ML-02-01`，尽管它现在属于线性代数A。理由是硬的：
> 这些代码被 2026 级选拔考卷引用着（17 道题，含**概念锚题**），
> 库里还有 **446 条学习事件、335 条掌握态**指向它们。
>
> **代码是身份，归属是属性。** 改属性不动任何证据；改身份要动整条纵向研究基线。
> 移交后实测：446 条事件、335 条掌握态、17 道题一条不少。
>
> 新建的知识点请用所属课程的前缀（见 `program_ai_zsb.yaml` 的 prefix 列）。

## 2.5 悬空需求队列：让"下一门课该建什么"由数据回答

这是这套方法里唯一真正新的一点：**拉取式不只用于教学，也用于图谱建设本身。**

**教师标注任务时，允许引用还不存在的知识点代码。**

```yaml
- T-DAC-3-5 | 拟合标定曲线与误差分析 | ... | 0 |
    DAC-05-10,DAC-05-11,ML-05-01,ML-05-02,LA-COND,PROB-ERR | ML-05-04,PROB-CI
```

`LA-COND`（矩阵条件数）、`PROB-ERR`（测量误差的正态性）在系统里还不存在。
这不是笔误，是教师在如实标注：**"这个任务确实要用，但那门课的图谱我们还没建"**。

系统不报错、不忽略，而是登记成需求：

```bash
$ make demand

  知识点代码          归属课程                     需求数  被谁需要
  COA-SETUP      计算机组成原理                    2  task:T-DAC-5-2、task:T-DAC-5-6
  EPS-CALIB      具身感知与多传感器融合                2  task:T-DAC-2-5、task:T-DAC-3-4
  EPS-SYNC       具身感知与多传感器融合                2  task:T-DAC-5-5、task:T-DAC-5-6
  PROB-ERR       概率论与数理统计A                  1  task:T-DAC-3-5
  ...

按课程汇总（哪门课欠得最多，就该先建哪门）：
  G18Z32012    具身感知与多传感器融合   欠 2 个知识点 / 被需求 4 次
  G18Z21025    计算机组成原理         欠 2 个知识点 / 被需求 3 次
```

**知识点一按该代码建出来，需求自动闭合**——队列会自己变短，不需要人去清。

### 照这个队列真建了一轮（2026-08 实录）

| 队列顺序 | 课程 | 欠几个点 | 实际建了 |
|---|---|---|---|
| 1 | 具身感知与多传感器融合 G18Z32012 | 2（被需求 4 次） | 24 |
| 2 | 计算机组成原理 G18Z21025 | 2（被需求 3 次） | 23 |
| 3 | 概率论与数理统计A G18Z21033 | 2 | 22 |
| 4 | 数据库与向量数据库 G18Z21026 | 2 | 23 |
| 5 | 线性代数A G18Z21032 | 1 | 21 |
| 6 | 面向对象程序设计 G18Z21027 | 1 | 21 |
| 7 | 算法与数据结构 G18Z21024 | 1 | 23 |
| 8 | Python语言程序设计 G18Z21021 | 1 | 22 |

**合计 179 个知识点，队列清空。**

注意"欠 1–2 个点"却建了 21–24 个：欠的那个知识点不是孤立的，
它在本课程内有自己的前置（要讲联合标定，得先有相机模型、坐标变换、内参标定）。
所以建的是**被拉取知识点在本课程内的前置闭包**，而不是整本教材。
这样每门课自然落在 20+ 个点上，刚好越过学分认定的第一道闸。

**高等数学B 没建**（只有从机器学习移交来的 5 个点），因为没有任何任务demand过它——
这不是遗漏，是拉取式该有的样子。哪天有项目要用泰勒展开，队列会说话。

> 一个必须说清的副作用：图谱从 284 个点长到 463 个点之后，
> 知识点自动匹配的 Top-6 召回率从 64.3% 掉到 **59.2%**。
> 不是算法退步了，是候选空间变大、标准答案也变多了。
> **图谱建得越全，字面匹配越难，教师审核这一关只会更重要，不会更轻松。**

于是"下一门课先建哪一部分"变成一个由数据回答的问题，
而不是由教务排期回答的问题。**28 门课不必平均用力**：
被 3 个项目拉过的那 20 个知识点，比没人拉的 300 个更该先建。

### 建设优先级（不是平均用力）

| | 特点 | 策略 |
|---|---|---|
| **数学三门**（高数/线代/概率） | 被**所有**项目拉取，内容十年不变，全校可共用一份 | **优先、一次性建好**，边际成本最低 |
| **程序设计/数据结构/组成原理** | 被同类工程项目反复拉取 | 第二梯队，仍值得整建 |
| **各专业方向课** | 只被特定项目拉取，且随产业变 | **拉取式建**，队列驱动 |

## 3. AI 自动匹配知识点：只提候选

```bash
make kpmatch A="propose PRJ-DAC"     # 生成候选
make kpmatch A="queue PRJ-DAC"       # 看待审队列
make kpmatch A="why 184"             # 让模型解释某一条
make kpmatch A="accept 184"          # 采纳 → 写入正式映射表
make kpmatch A="eval PRJ-DAC"        # 拿导师标注当标准答案自测
```

也可以在教师工作台的**映射审核**页里点（`/teacher/` → 项目制教学 → 映射审核）。

### 它怎么算的

| 环节 | 谁来做 | 换掉模型会怎样 |
|---|---|---|
| 算「这个任务像哪些知识点」 | 确定性检索（`packages/tools/lexmatch.py`） | 候选与分数一个字不变 |
| 沿依赖边补出前置知识点 | 知识图谱 | 不变 |
| 写一句「为什么可能相关」 | 大模型 | 退化为确定性说明，仅此而已 |
| **决定算不算数** | **教师** | — |

中文分词用字符二元组，不引入 jieba（零依赖是硬约束）。
不用向量的理由是**可解释性**：教师审候选时要看见
「因为命中了『编码器/四倍频/PSO』」，而不是「余弦相似度 0.83」。
教师不信任的候选，再准也不会被采纳。

### 依赖边扩展：召回率 44.4% → 59.2%

字面匹配有个天生盲区：任务说「训练一个分类模型」，字面上完全提不到
「无泄漏切分」——可它就是做这件事必须先会的。

而这恰恰是知识图谱存在的理由。所以匹配完之后，会把命中知识点的**前置**也提为候选：

```
Top-6 召回率：44.4%  →  59.2%（追一层）  →  62.1%（追两层）
每任务平均候选数：5.0  →   7.0           →   9.2
```

追两层收益递减而队列变长，不划算，默认只追一层。
参数在 `config.yaml` 的 `kpmatch_expand_top` / `kpmatch_expand_depth`。

扩展出来的候选一律**降置信度、标 helpful、写明「因为谁」**——
它是推理来的，不是文本证据，教师一眼要能看出这条是怎么冒出来的。

### 实测（拿导师已标注的 154 条映射当标准答案）

```
Top-6 召回率：100/169 = 59.2%
Top-1 命中任务数：27/41 = 65.9%
```

**召回率不是 100% 是正常的，也不打算追到 100%。** 导师会标进一些字面完全不相关、
但工程上确实需要的知识点，那部分机器替代不了——这正是它只做候选、不做决定的原因。

## 4. 红线：候选不是事实

|  | 模型提的候选 | 教师采纳后 |
|---|---|---|
| 存在哪 | `task_kp_candidate`（待审队列） | `task_kp_link`（正式映射表） |
| 署名 | `matcher`（算法版本） | **`teacher`** |
| 影响缺口计算 | 否 | 是 |
| 影响学分认定 | 否 | 是 |
| 否决之后 | 记住，下次不再提出 | — |

**整张候选表删掉，拉取式调度照常工作**——只是教师要手工标注而已。

这条红线由 `tests/test_layering.py::test_kpmatch_never_writes_the_real_mapping`
静态固化：匹配模块里一旦出现 `link_task_kp` 或 `decide_candidate`，`make check` 直接失败。

同一条规矩也用在模型出的题上：`origin=llm` 的题一律 `teacher_verified=0`，
教师确认前不得发给学生。

> **界面上刻意没有「一键采纳全部高置信度」按钮。**
> 映射是学分认定的依据，一条一条看是它应得的成本。真做了那个按钮，
> 点下去的那一刻，「导师标注」就悄悄变回了「模型推测」，而且看不出来。

## 5. 写适配器：把项目痕迹变成能力证据

新项目接入 = 实现 `packages/adapters/base.py` 的 `ProjectAdapter`，**不改核心代码**。

```python
@register("dac3d")
class DAC3DAdapter:
    project_type = "optics_inspection"

    def collect(self, since=None) -> list[ProjectSignal]: ...
```

DAC-3D 适配器从项目真实 git 仓库读到：

| 信号类 | 读什么 | 能说明什么 |
|---|---|---|
| `code_commit` | 提交次数、单次变更行数 | 投入与工作粒度 |
| `build_test` | 改动是否带上测试 | 工程质量意识 |
| `doc_delivery` | 文档类提交 | 技术表达 |
| `collaboration` | 被评审接受的合并 | 协作与被认可度 |
| `runtime` | 软件在环跑批完成率 | 系统真的跑通了没有 |

```bash
make signals          # 采集全部项目
```

### 作者映射由导师维护，系统不猜

git 里只有邮箱，系统里只有学号。映射表在
[`data/adapters/dac3d.yaml`](../data/adapters/dac3d.example.yaml)（模板在 `dac3d.example.yaml`）：

```yaml
authors:
  "zheng.ritchie@gmail.com": "2026001"
ignore:
  - "noreply@anthropic.com"     # 不是人，不代表学生工作量
```

**映射不到的作者直接跳过。** 宁可少记，也不能把工作量记到别人头上——
猜错一次，这条证据链就废了，而且废得看不出来。

真实配置**不入库**：`authors` 是邮箱到学号的身份关联，属个人信息，
按本仓库的 PII 规矩（同 `*.xlsx`）只留在本机，git 里只有 `dac3d.example.yaml` 模板。
服务器上通常只有模板，`authors` 为空 → 一条信号也不产出，而不是记错人。

### 可选能力：`task_corpus()`

适配器还可以交出**任务语料**，喂给知识点匹配当输入：

```python
def task_corpus(self) -> dict[str, str]:   # 任务代码 → 额外语料
```

DAC-3D 的实现从两处取：每一关的验收清单，以及该关「对应模块」点名的源码文件的
模块文档字符串。这是召回率的关键——任务名「关卡五 硬件同步触发」只有 8 个字，
把清单那几行喂进来，才能带上 `encoder_decoder.v`、PSO、触发延迟补偿这些真正的线索。

核心代码用 `hasattr` 探测这个方法，没有就退回只用任务名匹配，不报错。

## 6.5 学分怎么认定：两道闸，拿不准就说判不了

培养方案要的不是"项目分到哪门课"，而是**"这门课能不能给他学分"**。

```bash
$ make program A="coverage 1"

学分认定两道闸：图谱已建 ≥20 个知识点，且覆盖度 ≥25%（培养方案 §4）

  课程                 已建  已验证  覆盖度  学分  认定  说明
  G18Z21030 高等数学B（上）  3     1    33%  4.5   —   图谱仅建 3 个点，判不了
  G18Z21032 线性代数A      5     1    20%  3.0   —   图谱仅建 5 个点，判不了
  G18Z21022 机器学习      128     4     3%  3.0   —   覆盖度未达 25%

  可认定学分合计：0.0
  另有 22 门课图谱尚未建设，无法认定
```

### 第一道闸：图谱建够了没有

高等数学只建了 3 个点、覆盖 33%——如果就此给 4.5 学分，那是**假精度**。
这属于**判不了**，不是判不合格。

「判不了 ≠ 判错」在这里和确定性判分是同一条规矩（CLAUDE.md 铁律 7）：
**拿不准时给个 ✓，比不给更糟**——它会让整套认定失去可信度，而且看不出来。

门槛在 `config.yaml`：`credit_min_kps`（默认 20）。

### 第二道闸：覆盖度门槛

来自培养方案 §4："知识点覆盖不足 25% 不予认定""所有认定结论必须可追溯到具体知识点节点"。

**分子只算「已验证掌握」**（跨时间再次做对），不算当堂做对——
学分是要进档案的东西，一次做对的证据强度不够（铁律 6）。

### 第三道：项目专有知识走集中实践环节

DAC 拉取的 232 个知识点里有 **97 个**（DMD 结构光、144 孔物料盘编号、
这台设备的触发时序）在任何理论课大纲里都没有。

这些知识**不能硬塞进某门理论课凑覆盖度**——硬凑一次，认定的可信度就没了。
但学生确实做了，也不该白做。培养方案里本来就有承接它的地方：**集中实践环节**。

```yaml
# program_ai_zsb.yaml
practice_bindings:
  - PRJ-DAC > G18Z41029 | DAC-3D 是一个完整的在研产业项目，作为专业综合实习的载体
```

绑定之后，专业综合实习的覆盖范围 = 自身知识点 ∪ 该项目的项目知识域：

```
◆G18Z41029 专业综合实习   97   0   0%  3.0  —
   经项目 PRJ-DAC 折算；另需 12 个里程碑通过导师验收，系统不代签
```

两条约束：

- **一个项目只能绑一门实践课**（主键约束）。绑两门等于同一份工作认两次学分。
- **实践环节的学分不能只看覆盖度。** 系统给出覆盖度与里程碑数量两项事实，
  **签字仍然是教师的事**——系统不代签。

### 三条不能松的规矩

1. **知识点归属唯一。** 覆盖度只算这门课**拥有**的知识点。
   "向量与矩阵运算"归线性代数A，机器学习只是依赖它——一松，学分就重复计了。
2. **项目专有知识只经实践环节折算，不进理论课。** 未绑定时一律不折算，如实显示。
3. **这是派生视图，不落表。** 全部从事件流与图谱现算，不存第二份真相。

> 配合培养方案的两项制度：**免听不免考**（理论课可自学，但必须参加统考）、
> **30/70 考核**（30% 笔试仍统考，70% 实践由项目证据折算）。
> 覆盖度回答的是 70% 那一半。

## 7. 接下一个项目要做什么

1. 写 `data/seed/course_<x>.yaml`（若该领域知识点在现有图谱里没有），
   登记进 `scripts/seed.py` 的 `COURSE_FILES`；
   属于培养方案已有课程的章节，用 `course:` 写明归属
2. 写 `data/seed/projects_<x>.yaml`，登记进 `PROJECT_FILES`；
   **需要但还没建的知识点照写**，系统会登记成需求
3. 写 `packages/adapters/<x>.py`，在 `registry.py` 的 import 行加一个名字
4. `make seed && make kpmatch A="propose PRJ-<X>"`
5. 教师审候选（`/teacher/` → 项目制教学 → 映射审核）
6. `make signals`
7. `make program A="map PRJ-<X>"` 看它铺到培养方案哪几门课，
   `make demand` 看接下来该建什么
8. 若该项目有大量项目专有知识，在 `program_ai_zsb.yaml` 里加一条
   `practice_bindings`，把它绑到对应的集中实践课程上

**接第 5 个和第 10 个适配器的成本应当相同。** 若某次接入需要在核心代码里写
`if project == ...`，那是架构出了问题，不是这个项目特殊。
