# 待教师团队拍板的参数

以下参数决定系统形态。**代码一律做成配置，但初值需教学经验给定。**
改配置的位置：`config.yaml`（复制 `config.example.yaml`）或环境变量，改完重启即可。
当前生效值可随时通过 `GET /api/config` 或界面【可审计性】页核对。

## 关于 #7 信号权重矩阵

当前初值（待标定）：

```yaml
signal_weights:
  code_commit:   {M2: 0.5, M7: 0.5}   # 提交行为 → 编程实现、工程协作
  build_test:    {M7: 0.6, M2: 0.4}   # 构建质量 → 工程质量意识、调试能力
  runtime:       {M5: 0.5, M6: 0.3, M3: 0.2}  # 运行结果 → 调优、部署、算法
  doc_delivery:  {M8: 0.8, M7: 0.2}   # 文档交付 → 技术表达
  collaboration: {M7: 0.7, M8: 0.3}   # 协作记录 → 团队协作
```

请各位导师补充回答一个更根本的问题：
**你在指导项目时，实际上是凭哪些迹象判断一个学生真的懂了？**
把这些迹象说清楚，才能转化为系统的信号。

## 关于 #8 诊断报告字段

当前实现的字段：

- 全班知识点掌握热力图
- Top 3 待攻克点 + 各自根因
- 典型错误归因（来自错误模式库）
- 下节课建议重点（可一键否决）
- 需个别介入的学生名单
- 本周主动使用率与降级热点

这一条最关键：**报告要让教师每天愿意打开，就必须直接回答他真正关心的问题。**
请明确说出你希望在课后第一时间看到哪几件事，多余的我们删掉。

## 关于 #14–16 复检节奏

这三个参数决定"陪到你真正掌握"的实际形态，也是最需要教学经验的一组。

当前初值下的实测：全班 67 个达标点里只有 24 个经得起隔周再考，另有 50 个已到期复检。
这个比例是高是低、复检队列多长才不会让学生疲惫，只有一线教师能判断。

一条已经定死的取舍：**衰减只用于提醒复检，绝不写回掌握度**。
掌握度必须始终等于事件流折叠的结果，否则整个可审计性就塌了。

## 关于 #5 降级尺度

学生反复卡住时，系统应坚持追问还是直接讲解？这个尺度由教学经验决定。

需要注意的是取舍方向已经定死了：降级是为了防止挫败感摧毁动机，
**不是为了让学生轻松**。所以问题不是"要不要降级"，而是"几次之后降"、"每级给多少"。
